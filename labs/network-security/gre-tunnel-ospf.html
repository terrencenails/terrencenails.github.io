Upgrading the GRE Tunnel to Dynamic Routing with OSPF

Took the GRE tunnel from the previous project and replaced its hand-configured static routes with OSPF — including a wildcard mask left broader than it needed to be, and why that turned out not to matter as much as expected.

// OBJECTIVE

Why this project

Static routes work, but they don't scale — every new subnet means a manual route added on every router that needs to reach it. This project starts from the working GRE tunnel built in the previous project and swaps its static routes for OSPF, so each router's LAN is learned automatically through the tunnel instead of typed in by hand.

// TEST

Discovering the adjacency alone isn't enough

✕ UNREACHABLE
05

Ping still fails — 0% success

Even with a full OSPF adjacency between the two routers, pinging across to the remote LAN fails completely. The routers agree they're neighbors, but neither has told OSPF about its actual LAN yet — an adjacency alone doesn't create routes to networks that were never advertised.

// BUILD

Advertising the LANs

⚠ BROADER THAN NEEDED
06

Router1 advertises its LAN with an oversized wildcard mask

Advertised Router1's LAN with network 10.10.10.0 0.255.255.255 area 0 — a wildcard mask far wider than the /24 actually in use. OSPF accepted it without complaint and connectivity still worked, because OSPF advertises the interface's actual configured subnet, not the mask in the network statement itself — the statement only decides which interfaces get pulled into the process. Still worth tightening in a real deployment: a mask this broad would match any interface on the router starting with 10., which could pull an unintended interface into OSPF later without anyone noticing.

07

Router3 advertises its LAN correctly

Added Router3's LAN to OSPF with a mask that matches the /24 exactly — 0.0.0.255 — the tighter, more deliberate version of the same command.

100% success — the route is now learned dynamically, not typed in by hand.

✓ REACHABLE
09

Router1 reaches Router3's LAN

Same result in the other direction — full connectivity restored, this time via OSPF instead of static routes.

10

Confirm the route is dynamic

Router3's routing table now shows Router1's LAN with an O (OSPF) code instead of the S (static) code from the previous project — clear proof the route is being learned, not manually maintained, along with its OSPF cost and the interface it arrived on.

Result: the same two LANs from the original tunnel project are reachable again — but this time through a route OSPF discovered on its own. Getting there took two adjacent but distinct steps: bringing up the OSPF adjacency itself (via the tunnel network), then separately advertising each LAN — a full adjacency alone didn't produce a single usable route until that second step happened.

// TAKEAWAYS

What this demonstrates

  • An OSPF adjacency reaching FULL only means two routers have synchronized their link-state databases — it says nothing about which networks are actually being advertised. Routes still depend on separate network statements for each LAN.
  • OSPF's network statement wildcard mask controls which interfaces are pulled into the process — it does not redefine the subnet that gets advertised. That's why a mask far broader than intended can still "work," even though it's a real anti-pattern worth tightening, since it could unintentionally enable OSPF on other interfaces later.
  • Testing after every configuration change — even ones that technically succeeded — is what surfaces gaps like "adjacency up, but still can't ping." Assuming success from a clean CLI output would have missed it.
  • Comparing the route code in the routing table (S for static vs. O for OSPF) is a fast, reliable way to confirm which mechanism is actually responsible for a route — useful anytime a network is migrating from static to dynamic routing rather than starting from scratch.

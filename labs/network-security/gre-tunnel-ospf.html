Upgrading the GRE Tunnel to Dynamic Routing with OSPF

Took the GRE tunnel from the previous project and replaced its hand-configured static routes with OSPF. During the lab I made one configuration mistake on Router1: I entered network 10.10.10.0 0.255.255.255 area 0 instead of the intended network 10.10.10.0 0.0.0.255 area 0. The mistake did not break this small topology, so I kept the screenshot and documented exactly why it still worked — and what risk it would create if left uncorrected.

// OBJECTIVE

Why this project

Static routes work, but they don't scale — every new subnet means a manual route added on every router that needs to reach it. This project starts from the working GRE tunnel built in the previous project and swaps its static routes for OSPF, so each router's LAN is learned automatically through the tunnel instead of typed in by hand.

// BUILD

Advertising the LANs

⚠ CONFIGURATION MISTAKE
06

Router1 LAN advertisement — incorrect wildcard mask

I entered network 10.10.10.0 0.255.255.255 area 0 on Router1. That was a mistake. For this lab, the intended command was network 10.10.10.0 0.0.0.255 area 0, which limits the match to the 10.10.10.0/24 range.

Entered by mistake: network 10.10.10.0 0.255.255.255 area 0
Should have been: network 10.10.10.0 0.0.0.255 area 0

Why did it still work? In an OSPF network statement, the wildcard mask is used to match interface IP addresses. With 0.255.255.255, only the first octet is fixed, so the command effectively matches any Router1 interface with a 10.x.x.x address. In this lab, Router1 only has one such interface — 10.10.10.1/24 — so OSPF still enabled itself on the intended LAN interface and advertised that interface's actual 10.10.10.0/24 prefix.

What happens if it is not corrected? Nothing immediately breaks in this topology, but the configuration is unnecessarily broad. If Router1 later receives another interface in the 10.0.0.0/8 range — for example 10.20.20.1/24 — this same statement could also enable OSPF on that interface in area 0. That could cause an unintended OSPF adjacency to form on that link and could advertise additional connected networks that were never meant to participate in OSPF.

The important distinction is that the broad wildcard does not turn 10.10.10.0/24 into a 10.0.0.0/8 route. It broadens which interface addresses can match the OSPF statement. The interface's own configured subnet is still what OSPF advertises.

Corrective action: In a production configuration, I would replace the broad statement with network 10.10.10.0 0.0.0.255 area 0 so only the intended LAN interface is matched.

// TAKEAWAYS

What this demonstrates

  • A FULL OSPF adjacency confirms that the neighbors completed database exchange, but it does not guarantee that a specific LAN prefix has been included in OSPF. The relevant interfaces still have to participate before the remote router can learn those routes.
  • The Router1 command network 10.10.10.0 0.255.255.255 area 0 was a configuration mistake. It still works in this lab only because 10.10.10.1 is Router1's only 10.x.x.x interface. The correct, tighter statement is network 10.10.10.0 0.0.0.255 area 0.
  • Testing after each configuration change surfaces gaps like “adjacency up, but still can't ping” instead of treating successful control-plane output as proof that the intended data-plane path is working.
  • Comparing route codes in the routing table — S for static versus O for OSPF — is a quick way to verify which routing mechanism is currently providing the path during a migration from static to dynamic routing.

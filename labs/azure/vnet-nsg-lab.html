VNet + NSG: Scoped SSH Access, Built Entirely via CLI

Built a Virtual Network, a Network Security Group, and a least-privilege inbound rule entirely from Azure Cloud Shell — no Portal wizards — then provisioned a VM inside the protected subnet to host the workload that rule is meant to guard.

// OBJECTIVE

Why this project

A Network Security Group is only as good as how narrowly its rules are scoped — it's easy to open port 22 to 0.0.0.0/0 "just to get it working" and never tighten it back down. This project builds a VNet and NSG from scratch using only the CLI (to demonstrate scripting proficiency over Portal click-throughs), then deliberately scopes the inbound SSH rule to a single /32 source instead of the common shortcut — the same least-privilege instinct behind the asymmetric IAM policy in the AWS project.

// SETUP

Opening Cloud Shell

01

Launch Cloud Shell and select Bash

Opened Cloud Shell from the Azure Portal toolbar and selected Bash over PowerShell. The point of doing this project through the CLI instead of the Portal's creation wizards isn't stylistic — every command run here is a line that could be dropped straight into a script or a CI/CD pipeline, whereas a sequence of Portal clicks can't be replayed, versioned, or reviewed the same way. That repeatability is the actual skill being demonstrated, not just "knowing where the buttons are."

IN PRODUCTION

Infrastructure changes would go through version-controlled, peer-reviewed infrastructure as code rather than interactive commands — a standard baseline for how cloud environments get built and changed.

02

Session ready

Cloud Shell connects and drops into a bash prompt. Worth noting up front: this session is ephemeral — no files or system changes persist beyond it. That matters later for anything written to local storage (like SSH keys), and it's also a reminder that Cloud Shell itself is a shared, Microsoft-managed container, not a machine I own or control — which is why its outbound IP address changes between sessions, something that actually caused a real troubleshooting detour later in this lab.

// BUILD

Creating the VNet and subnet

03

Issue the VNet creation command

One command creates both the VNet and its subnet together — a /16 address space (10.0.0.0/16) with a /24 subnet (10.0.1.0/24) carved out of it. The /16 is deliberately oversized for what this lab actually needs (one subnet, one VM); the reasoning is the same one real network designers use — allocate address space with room to grow, so adding a second or third subnet later doesn't mean re-addressing the whole VNet. A /24 subnet inside it is still 251 usable host addresses, far more than this lab uses, but it keeps the boundary clean and easy to reason about.

✓ SUCCEEDED
04

VNet and subnet confirmed

Full JSON confirmation: lab-vnet and lab-subnet both show provisioningState: Succeeded. This is the CLI equivalent of what the Portal wizard would have produced — just scriptable and repeatable instead of click-through. Confirming the result explicitly here, rather than assuming the command "probably worked," is the same instinct as testing after every step in the network security labs: a command returning without an error isn't the same as confirming the resource actually exists in the state expected.

WHAT THE OUTPUT MEANS

"provisioningState": "Succeeded" is Azure confirming the resource actually finished being created, not just that the request was accepted. Seeing it on both the VNet and the subnet confirms both exist.

// BUILD

Creating the NSG

05

Create an empty NSG

Created lab-nsg with no custom rules yet — just Azure's default baseline. Creating the NSG as a completely separate step, before attaching it to anything or adding any custom rules, is deliberate: it lets the default posture be inspected and understood in isolation. If the NSG were created and immediately loaded with a custom rule in the same breath, it would be much harder to say with certainty which behavior came from Azure's defaults and which came from something added — and that distinction matters when something doesn't work as expected later.

WHAT THIS DOES

az network nsg create creates a new, empty firewall-like object — it doesn't filter anything yet on its own until it's attached to a subnet or network interface, which happens in a later step.

// VERIFY

Confirming the build in the Portal

CLI output is the primary evidence throughout this project, but it's worth cross-checking against the Portal — partly to confirm the CLI and the Portal agree, partly because a reviewer skimming a write-up finds a Portal screenshot easier to parse at a glance than raw JSON.

06

VNet visible in the Portal

lab-vnet shows up under Virtual networks, correctly placed in southcentralus — confirming the CLI-created resource is identical to what a Portal-driven build would show. This cross-check matters because the CLI and the Portal are two different clients hitting the same Azure Resource Manager API underneath — if they ever disagreed, that would point to a caching or propagation problem worth investigating, not just a display quirk.

07

Resource group holds both resources

The resource group view confirms both lab-nsg and lab-vnet exist side by side — a clean, minimal footprint with nothing extraneous. Keeping a lab's resource group free of leftover or unrelated resources isn't just tidiness — in a real environment, resource groups are usually the unit that cost, access, and lifecycle policies get applied to, so an resource group that accumulates unrelated clutter makes it much harder to reason about blast radius if something in it needs to be locked down or deleted.

✓ DEFAULT-DENY CONFIRMED
08

NSG's default baseline, before any custom rules

Zero custom rules, but the default rule set is already doing real work: AllowVnetInBound and AllowAzureLoadBalancerInBound at the top, DenyAllInBound underneath everything else. This is the actual starting security posture — worth screenshotting on its own before touching anything, so the "before" state is on record. The reason this matters beyond documentation: it proves the NSG is deny-by-default from the moment it exists, meaning every subsequent rule added is an explicit, auditable exception to that default — not one relaxation layered on top of an already-permissive baseline.

// BUILD

Associating the NSG with the subnet

✓ ASSOCIATED
09

Attach the NSG to lab-subnet

An NSG that exists but isn't attached to anything filters nothing. This command binds lab-nsg to lab-subnet — the result's networkSecurityGroup field confirms the association took. Binding at the subnet level rather than at an individual VM's network interface is a deliberate choice: a subnet-level NSG automatically covers every resource placed in that subnet in the future, which is the pattern that scales — a NIC-level-only approach means remembering to attach a policy every single time a new VM is added, which is exactly the kind of manual step that eventually gets forgotten.

WHAT THIS DOES

az network vnet subnet update attaches the NSG to the subnet by name. The returned networkSecurityGroup field pointing at lab-nsg is the confirmation that the attachment actually took.

10

Confirm zero custom rules, via CLI

Querying custom rules directly returns nothing — matching the Portal view from Step 08, and confirming the baseline state one more way before adding the actual allow rule. Two independent confirmations of the same "nothing here yet" state might look redundant, but it closes off the possibility that either the Portal or the CLI is caching a stale view — a small thing, but it's the difference between assuming a clean slate and actually knowing it.

// BUILD

Writing a least-privilege SSH rule

The common shortcut here is an inbound allow rule for port 22 scoped to 0.0.0.0/0 — any source. That works, but it's the exact pattern a security review would flag. This rule is scoped to a single address instead.

11

Find the source IP to scope the rule to

curl ifconfig.me returns Cloud Shell's own outbound IP — the address that would actually be doing the connecting. This step exists specifically to avoid the 0.0.0.0/0 shortcut: an inbound rule can only be as narrow as the source address it's actually written against, so the real address doing the connecting has to be known first. Worth noting this is Cloud Shell's Microsoft-managed egress IP, not a home or office IP, and it can change if the session recycles — which is exactly what happened later in this lab and had to be diagnosed.

WHAT THIS DOES

curl ifconfig.me asks a public web service "what IP address is this request coming from?" — a quick way to find your own outbound address without checking network settings manually.

✓ RULE CREATED
12

Create the scoped allow rule

Priority 100 — well ahead of the default rules at 65000+ — allowing TCP/22 inbound from that one address only (/32), not a range. Least-privilege by source and by port. The priority number is what actually decides outcome here: NSG rules are evaluated lowest-number-first, and the first matching rule wins, so a rule sitting at priority 100 is guaranteed to be evaluated well before the implicit deny at 65500 — without that low number, the rule would exist but never actually get a chance to apply.

WHAT THIS DOES

az network nsg rule create adds one allow rule to the NSG: which port (22), which protocol (TCP), which source address, and where it ranks (--priority 100) relative to every other rule.

IN PRODUCTION

Source addresses would come from a maintained, version-tracked definition rather than a value edited by hand against a live environment whenever it changes.

✓ ACTIVE, ABOVE DEFAULT DENY
13

Confirm the rule in the Portal

Allow-SSH-MyIP now sits at priority 100, above DenyAllInBound at 65500 — exactly where it needs to be to actually take effect. Custom security rules count moved from 0 to 1. Confirming the rule's position relative to the deny rule — not just that it exists — is the point: a rule with a priority number placed incorrectly (say, above 65500) would simply never be reached, and would look identical to a correctly-placed rule if you only checked for its existence rather than its ordering.

IN PRODUCTION

Centralized logging and alerting would be enabled from day one, following standard security monitoring baselines, rather than relying on manual point-in-time checks.

Result: the NSG went from a bare default-deny baseline to a deliberately narrow exception — one rule, one port, one exact source address, sitting well above the implicit deny. Every step was verified twice, once via CLI JSON and once via the Portal, rather than trusting either view alone.

// BUILD

Provisioning a VM inside the protected subnet

14

Deploy a VM with no NIC-level NSG

Created lab-vm inside lab-subnet with --nsg-rule NONE — deliberately preventing Azure from auto-creating a second NSG on the network interface itself. That matters: if both a subnet-level and a NIC-level NSG existed, it would be ambiguous which one was actually responsible for filtering traffic, and troubleshooting a connectivity problem later would mean checking two separate rule sets instead of one. This way, lab-nsg is the single source of truth for anything reaching this VM — one policy, one place to look, one place to audit.

IN PRODUCTION

Management interfaces wouldn't be exposed to the public internet at all — a standard access-control baseline — removing this exposure at the source rather than depending on a rule to catch every attempt against it.

Result: a working VM now sits behind a network boundary that only admits one specific address on one specific port — everything else, including all other inbound traffic types and sources, is denied by default. The VM is the workload; the NSG rule built in this project is what decides who's allowed to reach it.

// TAKEAWAYS

What this demonstrates

  • Every resource in this build — VNet, subnet, NSG, rule, VM — was created and verified through the CLI, not the Portal wizard. The Portal was used only to cross-check, never to build.
  • Scoping an inbound rule to a single /32 source instead of 0.0.0.0/0 costs nothing extra to configure, but it's the difference between "technically works" and actually least-privilege — the same discipline as the asymmetric IAM policy in the AWS project.
  • Rule priority is what actually determines behavior, not just the presence of an allow rule — Allow-SSH-MyIP only works because it sits at priority 100, well ahead of the implicit deny at 65500.

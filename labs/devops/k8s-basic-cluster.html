Building a Basic Kubernetes Cluster

Bootstrapped a single-node Kubernetes cluster from a bare Linux host with kubeadm — control plane init, pod networking, and a scaled, exposed nginx deployment — entirely from the command line.

Kubernetes
kubeadm
kubectl
Flannel CNI
// LAB NOTE

Training environment and redactions

⚠ LAB ENVIRONMENT — IDENTIFIERS SHOWN INTENTIONALLY

This project was completed in a disposable training environment. Screenshots may show lab-only values such as the temporary Cloud Server public IP, SSH host fingerprint, internal Kubernetes addresses, generated object identifiers, and the temporary kubeadm join command.

In production documentation, credentials and bootstrap tokens would be redacted, and environment-specific IP addresses, fingerprints, internal naming, and other operational identifiers would be hidden when they are not required for the procedure.

// PREPARE

Access the terminal and verify the cluster prerequisites

Use the Lab Credentials and Instant Terminal to log into the control plane node and confirm its automated setup finished. You will then verify the tools needed to build the cluster.

01

Connect to the control plane node

Wait until the Lab Credentials section is available, copy the Public IP under Cloud Server, and open Instant Terminal. At the terminal prompt, replace <<Public IP>> with the copied address and run:

COMMAND

ssh cloud_user@<<Public IP>>

When prompted to continue connecting, enter y. When prompted for the password, copy the Password from the Cloud Server section, return to the terminal, paste it, and press Enter.

If the prompt shows @ip instead of @controlplane, press Control+D to log out, wait 30 seconds, and connect again. The expected prompt is cloud_user@controlplane; hostname assignment can take two to three minutes.

IN PRODUCTION

The lab public IP and SSH fingerprint are shown for training visibility. Production documentation would normally redact environment-specific connection details when they are not required.

02

Confirm setup completed and verify the prerequisites

Confirm the instance finished its automated setup:

COMMANDS
  • ls setup-complete — expected output is the setup-complete file. If it is not listed yet, wait a minute and try again.
  • kubeadm version — verifies kubeadm is installed.
  • kubectl version --client — verifies kubectl is installed.
  • systemctl status containerd — verifies containerd is running. Enter q to exit the status command.

Result: successfully connected to the control plane node and verified the prerequisites for building the cluster.

// INITIALIZE

Initialize the Kubernetes cluster with kubeadm

Confirm the node meets the requirements for a Kubernetes control plane, then initialize the cluster and configure kubectl access to it.

03

Confirm swap is disabled and initialize the control plane

Confirm swap is disabled:

COMMAND

swapon --show

No output confirms that swap is disabled, which this lab requires. Then initialize the cluster control plane:

COMMAND

sudo kubeadm init --pod-network-cidr=10.244.0.0/16

When prompted with [sudo] password for cloud_user:, enter the Password from the Cloud Server section and press Enter. The password is not shown on screen. sudo caches the credential for a few minutes, so later sudo commands may not prompt again.

✓ CONTROL PLANE INITIALIZED
04

Confirm kubeadm initialization succeeded

The expected output includes Your Kubernetes control-plane has initialized successfully! along with a kubeadm join command for adding worker nodes.

IN PRODUCTION

The kubeadm join command contains a bootstrap token. It is intentionally visible in this disposable lab screenshot, but it should be redacted from production documentation.

05

Set up kubeconfig for cloud_user

Configure kubectl access for cloud_user with the commands provided by kubeadm:

COMMAND

mkdir -p $HOME/.kube && \
sudo cp /etc/kubernetes/admin.conf $HOME/.kube/config && \
sudo chown $(id -u):$(id -g) $HOME/.kube/config

If sudo prompts for a password, enter the Password from the Cloud Server section and press Enter.

IN PRODUCTION

/etc/kubernetes/admin.conf contains highly privileged cluster credentials. Production users would normally receive appropriately scoped access rather than sharing an administrative kubeconfig.

06

Confirm kubectl can reach the API server

COMMAND

kubectl cluster-info

The expected output displays the Kubernetes control plane endpoint, confirming API server connectivity.

⚠ NOT READY — EXPECTED
07

Check the node and system pods before networking is installed

COMMANDS
  • kubectl get nodes — expected node status is NotReady.
  • kubectl get pods -n kube-system — expected CoreDNS status is Pending.

This is expected because the cluster does not yet have a CNI plugin installed to manage pod networking.

Result: successfully initialized the Kubernetes control plane with kubeadm and configured kubectl access to it.

// NETWORK

Configure cluster networking and make the node schedulable

Apply the CNI plugin staged on the node so pods can communicate across the cluster, then remove the control-plane taint so the single node can run application workloads.

✓ NODE READY
08

Apply Flannel and remove the control-plane taint

COMMANDS
  • kubectl apply -f kube-flannel.yml — applies the pre-staged Flannel CNI manifest.
  • kubectl get pods -n kube-flannel — confirms the Flannel pods are running.
  • kubectl get nodes — expected node status is now Ready.
  • kubectl get pods -n kube-system — confirms the system pods are now running.
  • kubectl describe node controlplane | grep Taints — displays the control-plane taint.
  • kubectl taint nodes --all node-role.kubernetes.io/control-plane- — removes the taint so application workloads can run on this single-node cluster.

The node-role.kubernetes.io/control-plane taint prevents regular pods from being scheduled onto the node. In a multi-node cluster, this keeps application workloads off the control plane. Because this lab has only one node, the taint must be removed before application pods can run.

Result: successfully configured cluster networking with Flannel and made the control plane node schedulable.

// DEPLOY

Deploy a web server application to the cluster

Create a Deployment that runs the nginx web server, confirm it is running, and review how kubectl translates the command into a full object specification.

09

Create the nginx Deployment

COMMANDS
  • kubectl create deployment globomantics-web --image=nginx:1.31
  • kubectl rollout status deployment/globomantics-web
  • kubectl get pods -o wide

The expected output shows the pod running and the NODE column showing controlplane, since it is the only node in the cluster.

10

Review the Deployment's generated configuration

COMMAND

kubectl get deployment globomantics-web -o yaml

The kubectl create deployment command builds the Deployment object specification, including the pod template, labels, and selector fields.

11

Scale the Deployment to two replicas

COMMANDS
  • kubectl scale deployment globomantics-web --replicas=2
  • kubectl get pods

The expected output lists two pods with a Running status and a READY value of 1/1.

Result: successfully deployed and scaled a web server application on the Kubernetes cluster.

// EXPOSE

Expose and verify access to the application

Expose the Deployment with a NodePort service, then verify access to the application from inside the control plane node.

12

Create the NodePort service and test the ClusterIP

COMMANDS
  • kubectl expose deployment globomantics-web --type=NodePort --port=80
  • kubectl get service globomantics-web
  • CLUSTER_IP=$(kubectl get service globomantics-web -o jsonpath='{.spec.clusterIP}')
  • curl http://$CLUSTER_IP

Record the port displayed in the PORT(S) column after 80:; this is the node port assigned to the service. Curling the ClusterIP from the control plane node should return the nginx welcome page HTML.

✓ APPLICATION REACHABLE
13

Test the NodePort from localhost

Replace <<node port>> with the port recorded in the previous step:

COMMAND

curl http://localhost:<<node port>>

The expected output is the nginx welcome page HTML, confirming the application is reachable through the NodePort from inside the control plane node.

Result: the Deployment is exposed through a NodePort service and the nginx application is reachable from the control plane node through both the service ClusterIP and the node port on localhost.

// TAKEAWAYS

What this demonstrates

  • A kubeadm cluster moves through distinct stages: host preparation, control-plane initialization, kubeconfig setup, CNI installation, and workload scheduling.
  • Flannel provides the pod-networking layer required before the node becomes Ready, and a single-node cluster requires removal of the control-plane taint before normal application pods can be scheduled there.
  • A Deployment can be created, inspected, and scaled through kubectl, while a NodePort Service provides a stable way to expose the nginx workload and test access from the control plane node.

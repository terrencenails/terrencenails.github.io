AWS IAM Access Control Validation: User, Group, MFA, and Permission Testing

Provisioned an IAM user and group with intentionally different S3 and EC2 permission levels, configured virtual MFA for console sign-in, then authenticated as the test user to validate allowed and denied actions in practice.

AWS IAM
Access Control

// OBJECTIVE

Why this project

Access control is easy to describe on paper and easy to misconfigure in practice. This project builds a dedicated IAM identity with group-based AWS managed policies, then tests the resulting permissions as that user by performing actions that should succeed and actions that should be denied.

Scope note: this lab intentionally uses AmazonS3FullAccess to contrast full S3 access with AmazonEC2ReadOnlyAccess. Because AmazonS3FullAccess is broader than a task-specific policy, this project demonstrates permission scoping and validation rather than a strict least-privilege implementation. A production least-privilege design would use a customer-managed policy limited to the exact S3 actions and resources required.

To demonstrate IAM resource creation from the command line, used AWS CloudShell to create a second IAM user resource. This is intentionally narrower than the earlier console workflow: create-user creates the IAM user object only; console credentials, group membership, permissions, and MFA require separate configuration.

Searched for AWS CloudShell from the console. CloudShell is a browser-based shell with AWS CLI installed, and it makes the credentials from the active console session available automatically so separate CLI credential configuration is not required.

Ran aws iam create-user --user-name Siri. The command created the IAM user resource and returned its user name, user ID, ARN, and creation timestamp. It did not create a console password, add Siri to DevGroup, attach permissions, or configure MFA; those are separate IAM operations.

// TAKEAWAYS

What this demonstrates

  • Group-based policy assignment centralizes shared identity-based permissions and makes them easier to manage consistently across users. Effective access can still be influenced by other applicable policy types, such as resource-based policies, permissions boundaries, session policies, and AWS Organizations policies.
  • Virtual MFA adds a second factor to the IAM user's console sign-in. Requiring MFA for specific API or CLI actions is a separate authorization design that can be implemented with MFA-aware policy conditions and temporary credentials.
  • Policy intent should be validated with real authorization tests. In this lab, successful S3 actions and denied EC2 modification attempts demonstrated the effective behavior of the test identity rather than relying only on policy names.
  • The lab intentionally uses asymmetric access — broad S3 access and read-only EC2 access — to make permission differences easy to observe. For a production least-privilege design, the S3 side should be narrowed to only the required actions and bucket/object ARNs.
  • The console and CLI both interact with IAM, but each CLI command performs a specific operation. aws iam create-user creates the user resource only; additional commands or infrastructure-as-code are needed to configure credentials, group membership, permissions, and MFA.
